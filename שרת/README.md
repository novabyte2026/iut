# הורדה מיוטיוב לדרייב

שירות שמקבל קישור יוטיוב ושומר את הקובץ בתיקייה בדרייב שלכם, בכל רזולוציה.

המערכת בנויה משני חצאים, וזו לא החלטה שרירותית — כל צד עושה בדיוק את מה
שהשני לא מסוגל לעשות:

| | `server/` — Railway | `src/` — Apps Script |
|---|---|---|
| yt-dlp, ffmpeg | ✅ בינאריים במכולה | ❌ אין הרצת תהליכים |
| 1080p ומעלה | ✅ ffmpeg ממזג רצועות נפרדות | ❌ אין ffmpeg |
| העלאה לדרייב אישי | ❌ דורש OAuth מלא | ✅ `ScriptApp.getOAuthToken()` |
| ממשק, תור, התראות | — | ✅ |

**הצד של דרייב הוא הסיבה האמיתית לפיצול.** חשבון שירות נראה כמו הפתרון
המתבקש להעלאה ישירה מהשרת, אבל אין לו מכסת אחסון משלו בדרייב, ולכן הוא לא
יכול להיות הבעלים של קבצים בדרייב אישי וההעלאה נכשלת ב־`storageQuotaExceeded`.
Apps Script מקבל טוקן לחשבון שלכם בחינם — בלי מסך הסכמה ובלי לאחסן
refresh token — ועוקף את הבעיה כולה.

---

## איך זה עובד

```
דף אינטרנט / טופס
        |
        v
   [ תור עבודות ]  ---- Script Properties
        |
        |  POST /api/jobs          -->  Railway: yt-dlp מוריד, ffmpeg ממזג
        |  GET  /api/jobs/:id      -->  {status, progress}   (פולינג)
        v
   Transfer.gs   (חלק אחר חלק)
        |
        |  Range: bytes=0-8388607        Content-Range: bytes 0-8388607/...
        |  <-------------------  Railway  -------------------> Drive
        v
   קובץ בדרייב  |  או: תיקייה עם שתי רצועות + פקודת מיזוג
```

Apps Script לא נוגע בסרטון עצמו: הוא מזמין עבודה, ממתין, ואז מעביר בייטים
מהשרת אל דרייב בלי להחזיק אותם. שני המסלולים החלופיים — Cobalt ו־RapidAPI —
נשארו נתמכים למי שמעדיף לא להקים שרת בכלל.

הקמת השרת מתועדת בנפרד ב־[`server/README.md`](server/README.md), כולל
הנקודה שתשבור לכם אותו: **יוטיוב חוסמת כתובות IP של ספקי ענן**, ונדרש קובץ
עוגיות. זה הפרט התפעולי היחיד שאין ממנו מנוס.

## איך מגיעים ל־1080p ומעלה

מעל 720p יוטיוב לא מגישה קובץ ממוזג. הווידאו והאודיו הם שני זרמים נפרדים,
ואיחודם דורש ffmpeg. יש שתי דרכים לעקוף את זה, ושתיהן ממומשות:

| אסטרטגיה | מה קורה | מתי לבחור |
|---|---|---|
| **`merged`** | הספק מריץ ffmpeg אצלו ומגיש קובץ אחד מוכן. Apps Script רק מעביר בייטים. | כשיש לכם מופע Cobalt. הכי נוח למשתמש. |
| **`dual`** | שתי רצועות נשמרות בתיקייה משלהן, יחד עם פקודת ffmpeg מוכנה. המיזוג נעשה אצלכם. | כשהספק לא יודע למזג, או כשאתם רוצים אפס תלות בו. |

`VIDEO_STRATEGY: 'auto'` ב־`Config.gs` בוחר לבד: `merged` אם הספק תומך, אחרת `dual`.

המיזוג במצב `dual` הוא **העתקת זרמים בלבד** ולכן נמשך שניות, לא דקות:

```bash
ffmpeg -i "שם - וידאו.mp4" -i "שם - אודיו.m4a" -c copy -movflags +faststart "שם.mp4"
```

הפקודה מוצגת בממשק עם כפתור העתקה, נשלחת במייל, ונכתבת כקובץ `איך למזג.txt`
לצד הרצועות בתיקייה — כדי שגם מי שפותח את התיקייה בעוד חודש יבין מה לעשות.

`Extractor.gs` מעדיף רצועות מאותה משפחת מכולות (mp4 עם m4a, webm עם weba)
בדיוק כדי שהמיזוג יעבוד בהעתקה בלבד. כשאין ברירה והצירוף מעורב, `Merge.gs`
מפנה את הפלט ל־mkv — המכולה היחידה שבולעת כל צירוף בלי קידוד מחדש.

מה שלא ריאלי הוא מיזוג בתוך Apps Script עצמו: היה צריך להחזיק את שני הזרמים
המלאים בזיכרון כדי לבנות את אינדקס ה־MP4, וזה נופל על מגבלת הזיכרון הרבה לפני
שהוא נופל על מגבלת ששת הדקות.

## שלוש המגבלות שהעיצוב מתמודד איתן

| מגבלה | הערך | הפתרון בקוד |
|---|---|---|
| גודל תשובה ל־`UrlFetchApp` | 50MB | `pumpPart_` מושך בנתחי 8MB עם כותרת `Range` ודוחף לסשן העלאה מתחדשת של Drive. הקובץ נבנה בצד של גוגל ואף פעם לא נמצא שלם בזיכרון. |
| זמן ריצה לביצוע | 6 דקות | כל נתח שנשלח נשמר במצב העבודה. כשנגמר תקציב הזמן העבודה נעצרת באמצע, וטריגר חד־פעמי ממשיך מאותו בייט — גם באמצע הרצועה השנייה. |
| אין ffmpeg | — | `merged` או `dual`, כמתואר למעלה. |

**התקרה האמיתית של השכבה החינמית** היא 90 דקות ריצת טריגרים ליום בחשבון Gmail
רגיל (6 שעות ב־Workspace). זה מתורגם לערך לשעה וחצי של זמן העברה ביום.

## התקנה

### 1. יצירת הפרויקט

צרו פרויקט חדש ב־[script.google.com](https://script.google.com) והעתיקו לתוכו את
הקבצים מתיקיית `src/`. לחלופין, עם [clasp](https://github.com/google/clasp):

```bash
npm i -g @google/clasp
clasp login
clasp create --type webapp --title "הורדה מיוטיוב לדרייב" --rootDir src
clasp push
```

כדי לראות את `appsscript.json` בעורך: Project Settings ואז סמנו
"Show appsscript.json manifest file in editor".

### 2. בחירת ספק חילוץ

**Railway (ברירת המחדל)** — השרת שבתיקיית `server/`. הקימו אותו לפי
[`server/README.md`](server/README.md), ואז ב־`Config.gs`:

```javascript
EXTRACTOR: 'railway',
RAILWAY_ENDPOINT: 'https://your-app.up.railway.app',
```

הטוקן נשמר ב־Script Properties תחת `RAILWAY_TOKEN` וחייב להיות זהה
ל־`SHARED_TOKEN` שהוגדר בשרת.

זה המסלול היחיד שנותן שליטה מלאה: אתם מריצים את yt-dlp, אתם מעדכנים אותו,
ואף אחד לא סוגר לכם את השירות באמצע. בתמורה אתם גם אלה שמתמודדים עם חסימת
הכתובות של יוטיוב — ראו את פרק העוגיות ב־README של השרת.

**Cobalt** — פרויקט קוד פתוח שאפשר להריץ בעצמכם. גם הוא ממזג אצלו ולכן נותן
1080p כקובץ אחד. מכונות ציבוריות חוסמות ברובן שימוש אוטומטי, כך שהרצה עצמית
היא דרישה מעשית ולא המלצה.

**RapidAPI** — מחזיר את רשימת הפורמטים הגולמית, ולכן זה המסלול היחיד שדרכו
עובד מצב `dual`. התאימו את `planWithRapidApi_` למבנה התשובה של הספק שבחרתם;
המבנה שונה בין ספקים וזו הפונקציה שתצטרכו לגעת בה.

בכל המסלולים הסוד נשמר ב־Script Properties ולא בקוד — ראו שלב 3.

### 3. שמירת סודות

פתחו את `Setup.gs`, בטלו את ההערה בשורות הרלוונטיות ב־`setupCredentials()`,
מלאו את הערכים, **הריצו את הפונקציה פעם אחת, ואז מחקו את הערכים מהקוד.**
מכאן הם חיים ב־Project Settings ואז Script Properties.

### 4. הרצה ראשונה

הריצו את `setup()` מהעורך. גוגל תבקש הרשאות — זה הרגע שבו הסקריפט מקבל גישה
לדרייב שלכם. הפונקציה יוצרת את תיקיית היעד ומתקינה טריגר רשת ביטחון.

אחר כך הריצו `testExtractor()`. היא בודקת כל רצועה בנפרד ומדפיסה את אסטרטגיית
החילוץ, גודל כל חלק, ואת פקודת המיזוג שתימסר. מספיק שרצועה אחת לא תומכת
ב־`Range` כדי שהעבודה תיתקע באמצע, ועדיף לגלות את זה כאן ולא אחרי 300MB.

### 5. פרסום

Deploy ואז New deployment ואז Web app.

| הגדרה | ערך |
|---|---|
| Execute as | **Me** — נדרש, כדי שהקבצים יישמרו בדרייב שלכם |
| Who has access | `Only myself` לשימוש אישי, `Anyone` אם פותחים לאחרים |

אם בחרתם `Anyone`, הפעילו הגנת סיסמה: `REQUIRE_PASSWORD: true` ב־`Config.gs`
ו־`WEB_PASSWORD` ב־Script Properties. בלי זה כל מי שמקבל את הקישור מוריד לדרייב
שלכם ועל חשבון המכסה שלכם.

## חיבור טופס Google Forms

אם אתם מעדיפים את הממשק הזה על פני דף אינטרנט:

1. בנו טופס: שאלת הקישור היא היחידה שחובה. אפשר להוסיף שאלת פורמט
   (וידאו/אודיו) ושאלת איכות (360…2160) — לא חובה, ולא משנה באיזה סדר.
2. בעורך התסריט של הטופס, קשרו אותו לפרויקט הזה.
3. הוסיפו טריגר: Triggers ואז Add Trigger, פונקציה `onFormSubmit`, מקור
   "From form", סוג "On form submit".

`onFormSubmit` מזהה כל שאלה לפי התוכן ולא לפי מיקומה: הקישור מזוהה כי הוא
כתובת יוטיוב, הפורמט לפי המילה "אודיו"/"audio", והאיכות לפי המספר שבתשובה.
לכן אפשר להוסיף, להסיר או לסדר מחדש שאלות (כולל שדה איסוף מייל) בלי לגעת
בקוד. שאלה שלא זוהתה פשוט מתעלמים ממנה; אם אין אף קישור יוטיוב, השליחה
לא פותחת עבודה.

## כפתור צף על יוטיוב, והורדת ערוץ שלם

קליינט שלישי, בתיקיית [`userscript/`](userscript/README.md): תוסף Tampermonkey
שמזריק כפתור ישירות לעמוד יוטיוב — בלי להעתיק קישור לשום מקום — ותומך גם
בהורדת ערוץ שלם בבת אחת עם דילוג אוטומטי על סרטונים שכבר ירדו.

זה דורש שכבת API חדשה ב־Apps Script, כי `google.script.run` עובד רק מתוך
הדף שה־Web App עצמו מגיש, וסקריפט חיצוני לא טוען את הדף בכלל:

| קובץ | תפקיד |
|---|---|
| `Api.gs` | `doPost(e)` — נקודת הכניסה ל־HTTP POST מקליינטים חיצוניים |
| `Channel.gs` | מניפסט עבודת ערוץ, ולוג דה־דופ פר־ערוץ בצד השרת |
| `server/src/routes/channel.js` | רשימת סרטוני ערוץ דרך `yt-dlp --flat-playlist` |

עבודת ערוץ לא ממציאה מנוע תור חדש — היא פשוט פותחת עבודה רגילה לכל סרטון
(אותו צינור חילוץ/מיזוג/העברה שכבר קיים), ומקשרת אותן למניפסט משותף
שמצטבר ככל שכל אחת מהן מסתיימת. `processQueue` הקיים כבר יודע לעבד הרבה
עבודות ממתינות על פני כמה ביצועים, אז זה עובד בלי שינוי במנוע עצמו.

**אין כאן מכסה יומית.** יש רק תקרה טכנית לכמה סרטונים נכנסים ללחיצה אחת
(`CHANNEL_BATCH_LIMIT`), כדי לא לפתוח אלפי עבודות בבת אחת — ערוץ גדול יותר
פשוט דורש עוד לחיצה, והדה־דופ מבטיח שכל לחיצה ממשיכה מאיפה שהקודמת עצרה.

הכלי אישי: הפריסה רצה עם `Execute as: Me`, כך שכל מה שמורידים ממנה — מהכפתור
הזה או מהדף הרגיל — נשמר בדרייב של מי שפרס אותה. לשתף עם אחרים דורש שלכל
אחד תהיה פריסה משלו, לא שיתוף פריסה אחת (אחרת ההורדות שלהם ייכנסו לדרייב
שלכם). פרטי ההתקנה המלאים ב־[`userscript/README.md`](userscript/README.md).

## אבחון תקלות

הריצו `showQueue()` כדי לראות את מצב כל העבודות, ו־`resetAll()` כדי לאפס
תור תקוע. הלוג המלא נמצא בעורך תחת Executions.

| תסמין | סיבה ופתרון |
|---|---|
| `המקור לא תומך בבקשות Range` | הספק החזיר כתובת פרוקסי בלי תמיכה בהעברה חלקית. קבצים מתחת ל־50MB עדיין יעבדו; מעל זה צריך ספק אחר. |
| `Cobalt לא חושף רצועות נפרדות` | ביקשתם `dual` מספק שיודע רק למזג. החזירו ל־`merged` או `auto`. |
| `רשומת העבודה חרגה מ־8800 בתים` | כתובות המדיה ארוכות במיוחד. תקרת Script Properties היא 9KB לערך. |
| `סשן ההעלאה פג` | סשן resumable תקף כשבוע. החלק יתחיל מחדש בניסיון הבא; חלקים שהושלמו לא ייפגעו. |
| `Exceeded maximum execution time` | תקציב הזמן גבוה מדי. הורידו את `TIME_BUDGET_MS`. |
| הכול נעצר בשקט אחרי יומיים | הגעתם לתקרת 20 הטריגרים. `cleanupTriggers_` אמור למנוע זאת; הריצו `resetAll()` ואז `setup()`. |
| `Service invoked too many times` | נגמרה מכסת ריצת הטריגרים היומית (90 דקות). ממתינים ליום הבא. |
| קיבלתי mkv במקום mp4 | הרצועות היו ממכולות שונות. זה תקין ומכוון — mkv מונע קידוד מחדש. |

## הערה משפטית

הורדת סרטונים מיוטיוב נוגדת את תנאי השימוש של השירות, למעט תוכן שאתם הבעלים
שלו, תוכן ברישיון פתוח, או הורדות דרך YouTube Premium. השימושים שהכלי הזה בנוי
עבורם הם ארכוב תוכן שלכם וגיבוי חומרים ברישיון חופשי.
